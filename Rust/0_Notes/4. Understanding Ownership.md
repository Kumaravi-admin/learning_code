## Understanding Ownership

Ownership Rust ka sabse unique feature hai aur iske baaki language par gehre implications hain. Yeh Rust ko bina garbage collector ke memory safety guarantees dene mein saksham banata hai, isliye yeh samajhna zaroori hai ki ownership kaise kaam karti hai. Is chapter mein, hum ownership ke saath-saath kai related features ke baare mein baat karenge: borrowing, slices, aur Rust memory mein data ko kaise layout karta hai.

---

## 1. What Is Ownership?

Ownership rules ka ek set hai jo yeh govern karta hai ki ek Rust program memory ko kaise manage karta hai. Saare programs ko computer ki memory use karne ke tareeke ko manage karna padta hai jab woh run ho rahe hote hain. Kuch languages mein garbage collection hoti hai jo program ke run hone par regularly un-used memory ko dhoondhti hai; doosri languages mein, programmer ko explicitly memory allocate aur free karni padti hai. Rust ek teesra approach use karta hai: memory _ownership_ ke ek system ke through manage ki jaati hai jisme rules ka ek set hota hai jise compiler check karta hai. Agar koi bhi rule violate hota hai, toh program compile nahi hoga. Ownership ka koi bhi feature aapke program ko tab slow nahi karega jab woh run ho raha hoga.

Kyunki ownership kai programmers ke liye ek naya concept hai, iski aadat padne mein thoda samay lagta hai. Acchi khabar yeh hai ki aap Rust aur ownership system ke rules ke saath jitne zyada experienced honge, utna hi aasaan aapke liye aisa code naturally develop karna hoga jo safe aur efficient ho. Lage rahein!

Jab aap ownership ko samajh lete hain, toh aapke paas un features ko samajhne ke liye ek solid foundation hogi jo Rust ko unique banate hain. Is chapter mein, aap kuch examples ke through kaam karke ownership seekhenge jo ek bahut common data structure par focus karte hain: strings.

## 2. The Stack and the Heap

Kai programming languages mein, aapko stack aur heap ke baare mein aksar sochne ki zaroorat nahi padti. Lekin Rust jaisi systems programming language mein, koi value stack par hai ya heap par, yeh is baat ko affect karta hai ki language kaise behave karti hai aur aapko kuch decisions kyun lene padte hain. Ownership ke hisson ko is chapter mein baad mein stack aur heap ke relation mein describe kiya jayega, isliye yahan taiyari ke taur par ek brief explanation di gayi hai.

Stack aur heap dono memory ke parts hain jo aapke code ko runtime par use karne ke liye available hote hain, lekin yeh alag-alag tareekon se structured hote hain. Stack values ko usi order mein store karta hai jis order mein woh use milti hain aur values ko opposite order mein remove karta hai. Ise _last in, first out_ kaha jaata hai. Plates ke ek stack ke baare mein sochein: jab aap aur plates add karte hain, toh aap unhe upar rakhte hain, aur jab aapko ek plate ki zaroorat hoti hai, toh aap ek plate upar se uthate hain. Beech ya neeche se plates add ya remove karna utni acchi tarah kaam nahi karega! Data add karne ko _pushing onto the stack_ kaha jaata hai, aur data remove karne ko _popping off the stack_ kaha jaata hai. Stack par store kiye gaye saare data ka ek known, fixed size hona zaroori hai. Jis data ka size compile time par unknown hai ya jiska size badal sakta hai, use iske bajaye heap par store kiya jaana chahiye.

Heap kam organized hota hai: jab aap heap par data rakhte hain, toh aap ek certain amount of space ki request karte hain. Memory allocator heap mein ek empty spot dhoondhta hai jo kaafi bada ho, use in-use ke roop mein mark karta hai, aur ek _pointer_ return karta hai, jo us location ka address hota hai. Is process ko _allocating on the heap_ kaha jaata hai aur kabhi-kabhi ise sirf _allocating_ ke roop mein abbreviate kiya jaata hai (stack par values push karne ko allocating nahi maana jaata). Kyunki heap ka pointer ek known, fixed size ka hota hai, aap pointer ko stack par store kar sakte hain, lekin jab aapko actual data chahiye hota hai, toh aapko pointer ko follow karna padta hai.

Ek restaurant mein baithne ke baare mein sochein. Jab aap enter karte hain, toh aap apne group mein logon ki sankhya batate hain, aur host ek empty table dhoondhta hai jo sabko fit kare aur aapko wahan le jaata hai. Agar aapke group mein koi late aata hai, toh woh pooch sakta hai ki aapko kahan bithaya gaya hai taaki aapko dhoondh sake.

Stack par push karna heap par allocate karne se fast hota hai kyunki allocator ko kabhi bhi naya data store karne ke liye jagah dhoondhni nahi padti; woh location hamesha stack ke top par hoti hai. Iske comparison mein, heap par space allocate karne mein zyada kaam lagta hai kyunki allocator ko pehle data ko hold karne ke liye kaafi badi space dhoondhni padti hai aur phir agli allocation ke liye taiyari karne ke liye bookkeeping karni padti hai.

Heap mein data ko access karna stack par data ko access karne se slow hota hai kyunki wahan pahunchne ke liye aapko ek pointer ko follow karna padta hai. Contemporary processors zyada fast hote hain agar woh memory mein kam idhar-udhar jump karte hain. Analogy ko jaari rakhte hue, ek restaurant mein ek server par vichar karein jo kai tables se orders le raha hai. Agli table par jaane se pehle ek table ke saare orders lena sabse efficient hota hai. Table A se ek order lena, phir table B se ek order lena, phir dobara A se ek, aur phir dobara B se ek lena ek bahut slow process hoga. Isi tarah, ek processor apna kaam behtar tareeke se kar sakta hai agar woh aise data par kaam kare jo doosre data ke close ho (jaise ki yeh stack par hota hai) bajaye iske ki woh door ho (jaise ki yeh heap par ho sakta hai).

Jab aapka code kisi function ko call karta hai, toh function mein pass ki gayi values (jisme heap par data ke pointers bhi shaamil ho sakte hain) aur function ke local variables stack par push ho jaate hain. Jab function khatam hota hai, toh woh values stack se pop off ho jaati hain.

Is baat ka track rakhna ki code ke kaunse parts heap par kaunsa data use kar rahe hain, heap par duplicate data ki amount ko minimize karna, aur heap par unused data ko clean up karna taaki aapke paas space khatam na ho, yeh sab woh problems hain jinhe ownership address karti hai. Ek baar jab aap ownership ko samajh lete hain, toh aapko stack aur heap ke baare mein aksar sochne ki zaroorat nahi padegi, lekin yeh jaanna ki ownership ka main purpose heap data ko manage karna hai, yeh samajhne mein help kar sakta hai ki yeh is tarah kyun kaam karti hai.

- Ek samay mein sirf ek hi owner ho sakta hai.
- Jab owner _scope_ se bahar jaata hai, toh value _drop_ kar di jayegi.

## 4. Variable Scope

Ab jabki hum basic Rust syntax se aage badh chuke hain, hum examples mein saara `fn main() {` code include nahi karenge, isliye agar aap saath-saath follow kar rahe hain, toh neeche diye gaye examples ko manually ek main function ke andar rakhna sunishchit karein. Nateeje ke taur par, hamare examples thode zyada concise honge, jisse hum boilerplate code ke bajaye actual details par focus kar payenge.

Ownership ke pehle example ke roop mein, hum kuch variables ke scope ko dekhenge. Ek _scope_ program ke andar woh range hoti hai jiske liye ek item valid hota hai. Neeche diya gaya variable lein:

```rust
let s = "hello";
```

Variable `s` ek string literal ko refer karta hai, jahan string ki value hamare program ke text mein hardcoded hai. Variable us point se valid hota hai jis point par ise declare kiya jaata hai jab tak ki current scope khatam nahi ho jaata. Listing 4-1 mein ek program dikhaya gaya hai jisme comments annotate karte hain ki variable `s` kahan valid hoga.

```rust
{                          // s yahan valid nahi hai, kyunki ise abhi declare nahi kiya gaya hai
    let s = "hello";       // s is point se aage valid hai

    // s ke saath kaam karein
}                          // yeh scope ab khatam ho gaya hai, aur s ab valid nahi hai
```

_Listing 4-1: Ek variable aur woh scope jisme yeh valid hai_

Doosre shabdon mein, yahan time ke do important points hain:

- Jab `s` scope mein _aata hai_, toh yeh valid hota hai.
- Yeh tab tak valid rehta hai jab tak yeh scope se _bahar nahi chala jaata_.

Is point par, scopes aur variables kab valid hote hain, iske beech ka relationship doosri programming languages jaisa hi hai. Ab hum is understanding ke upar build karenge aur `String` type ko introduce karenge.

## 5. The String Type

Ownership ke rules ko illustrate karne ke liye, humein ek aise data type ki zaroorat hai jo un types se zyada complex ho jinhe humne Chapter 3 ke “Data Types” section mein cover kiya tha. Pehle cover kiye gaye types ek known size ke hote hain, unhe stack par store kiya ja sakta hai aur jab unka scope khatam hota hai toh unhe stack se pop off kiya ja sakta hai, aur agar code ke kisi doosre part ko ek different scope mein wahi value use karne ki zaroorat ho, toh ek naya, independent instance banane ke liye unhe jaldi aur aasani se copy kiya ja sakta hai. Lekin hum aise data ko dekhna chahte hain jo heap par store hota hai aur explore karna chahte hain ki Rust ko kaise pata chalta hai ki us data ko kab clean up karna hai, aur `String` type ek behtareen example hai.

Hum `String` ke un parts par focus karenge jo ownership se relate karte hain. Yeh aspects doosre complex data types par bhi apply hote hain, chahe woh standard library dwara provide kiye gaye hon ya aapke dwara banaye gaye hon. Hum `String` ke baare mein Chapter 8 mein zyada gehrai se discuss karenge.

Hum pehle hi string literals dekh chuke hain, jahan ek string value hamare program mein hardcoded hoti hai. String literals convenient hote hain, lekin woh har situation ke liye suitable nahi hote jisme hum text use karna chah sakte hain. Ek wajah yeh hai ki woh immutable hote hain. Doosri wajah yeh hai ki har string value tab nahi jaani ja sakti jab hum apna code likhte hain: example ke liye, kya hoga agar hum user input lena chahte hain aur use store karna chahte hain? In situations ke liye, Rust ke paas ek doosra string type hai, `String`. Yeh type heap par allocate kiye gaye data ko manage karta hai aur is wajah se yeh text ki ek aisi amount store karne mein saksham hai jo humein compile time par unknown hoti hai. Aap `from` function ka use karke ek string literal se ek `String` bana sakte hain, kuch is tarah:

```rust
let s = String::from("hello");
```

Double colon `::` operator humein is particular `from` function ko `String` type ke under namespace karne deta hai bajaye iske ki kisi tarah ke name jaise `string_from` ka use kiya jaye. Hum is syntax ke baare mein Chapter 5 ke “Method Syntax” section mein aur Chapter 7 mein “Paths for Referring to an Item in the Module Tree” mein jab modules mein namespacing ke baare mein baat karenge, tab aur zyada discuss karenge.

Is tarah ki string ko mutate (badla) ja sakta hai:

```rust
let mut s = String::from("hello");

s.push_str(", world!"); // push_str() ek String mein literal append karta hai

println!("{s}"); // yeh `hello, world!` print karega
```

**Output:**

```shell
$ cargo run
hello, world!
```

Toh, yahan kya difference hai? `String` ko mutate kyun kiya ja sakta hai lekin literals ko kyun nahi? Difference is baat mein hai ki yeh dono types memory ko kaise deal karte hain.

## 6. Memory and Allocation

Ek string literal ke case mein, hum compile time par content jaante hain, isliye text seedhe final executable mein hardcode kar diya jaata hai. Yahi wajah hai ki string literals fast aur efficient hote hain. Lekin yeh properties sirf string literal ki immutability se aati hain. Afsos ki baat hai ki hum binary mein text ke har us piece ke liye memory ka ek blob nahi daal sakte jiska size compile time par unknown hai aur jiska size program run hone ke dauran badal sakta hai.

`String` type ke saath, ek mutable, growable piece of text ko support karne ke liye, humein heap par memory ki ek amount allocate karne ki zaroorat hoti hai, jo compile time par unknown hoti hai, taaki content ko hold kiya ja sake. Iska matlab hai:

- Memory ko runtime par memory allocator se request kiya jaana chahiye.
- Jab hum apna `String` ke saath kaam poora kar lein, toh humein is memory ko allocator ko wapas return karne ka ek tareeka chahiye.

Woh pehla part hamare dwara kiya jaata hai: jab hum `String::from` call karte hain, toh iski implementation us memory ki request karti hai jiski ise zaroorat hoti hai. Yeh programming languages mein lagbhag universal hai.

Halanki, doosra part alag hai. Garbage collector (GC) wali languages mein, GC track rakhta hai aur us memory ko clean up karta hai jiska ab use nahi ho raha hai, aur humein iske baare mein sochne ki zaroorat nahi hoti. Bina GC wali zyada tar languages mein, yeh identify karna hamari responsibility hoti hai ki memory kab ab use mein nahi hai aur ise explicitly free karne ke liye code call karna padta hai, bilkul waise hi jaise humne ise request kiya tha. Ise sahi tareeke se karna historically ek difficult programming problem raha hai. Agar hum bhool jaate hain, toh hum memory waste karenge. Agar hum ise bahut jaldi kar dete hain, toh hamare paas ek invalid variable hoga. Agar hum ise do baar kar dete hain, toh woh bhi ek bug hai. Humein bilkul ek allocate ko bilkul ek free ke saath pair karna hoga.

Rust ek alag path leta hai: jis variable ke paas memory hoti hai, jab woh scope se bahar jaata hai toh memory automatically return kar di jaati hai. Yahan Listing 4-1 se hamare scope example ka ek version hai jo string literal ke bajaye `String` ka use karta hai:

```rust
{
    let s = String::from("hello"); // s is point se aage valid hai

    // s ke saath kaam karein
}                                  // yeh scope ab khatam ho gaya hai, aur s ab
                                   // valid nahi hai
```

Ek natural point hai jahan hum apne `String` ko chahiye memory ko allocator ko return kar sakte hain: jab `s` scope se bahar jaata hai. Jab ek variable scope se bahar jaata hai, toh Rust hamare liye ek special function call karta hai. Is function ko `drop` kaha jaata hai, aur yahi woh jagah hai jahan `String` ka author memory ko return karne ka code rakh sakta hai. Rust closing curly bracket par `drop` ko automatically call karta hai.

> Note: C++ mein, kisi item ke lifetime ke end par resources ko deallocate karne ke is pattern ko kabhi-kabhi _Resource Acquisition Is Initialization_ (RAII) kaha jaata hai. Rust mein `drop` function aapko familiar lagega agar aapne RAII patterns use kiye hain.

Is pattern ka Rust code likhne ke tareeke par gehra impact padta hai. Yeh abhi simple lag sakta hai, lekin zyada complicated situations mein code ka behavior unexpected ho sakta hai jab hum chahte hain ki multiple variables us data ko use karein jise humne heap par allocate kiya hai. Aaiye ab unmein se kuch situations ko explore karein.

## 7. Variables and Data Interacting with Move

Rust mein multiple variables ek hi data ke saath alag-alag tareekon se interact kar sakte hain. Aaiye Listing 4-2 mein integers ka use karte hue ek example dekhein.

```rust
let x = 5;
let y = x;
```

_Listing 4-2: Variable `x` ki integer value ko `y` mein assign karna_

Hum shayad andaza laga sakte hain ki yeh kya kar raha hai: “`5` value ko `x` se bind karein; phir `x` mein maujood value ki ek copy banayein aur use `y` se bind karein.” Ab hamare paas do variables hain, `x` aur `y`, aur dono `5` ke barabar hain. Dar-asal yahi ho raha hai, kyunki integers ek known, fixed size wali simple values hain, aur yeh dono `5` values stack par push ho jaati hain.

Ab aaiye `String` version dekhein:

```rust
let s1 = String::from("hello");
let s2 = s1;
```

Yeh bahut similar dikhta hai, isliye hum assume kar sakte hain ki iske kaam karne ka tareeka wahi hoga: yani, doosri line `s1` mein maujood value ki ek copy banayegi aur use `s2` se bind karegi. Lekin bilkul aisa nahi hota hai.

Yeh dekhne ke liye ki under the covers `String` ke saath kya ho raha hai, Figure 4-1 dekhein. Ek `String` teen parts se milkar bana hota hai, jo left par dikhaye gaye hain: memory ka ek pointer jo string ke contents ko hold karta hai, ek length, aur ek capacity. Data ka yeh group stack par store hota hai. Right par heap par maujood memory hai jo contents ko hold karti hai.

├──────────┼───────┤         ├───────┼───────┤

Length aur capacity ke beech ka difference matter karta hai, lekin is context mein nahi, isliye abhi ke liye, capacity ko ignore karna theek hai.

Jab hum `s1` ko `s2` mein assign karte hain, toh `String` data copy hota hai, jiska matlab hai ki hum stack par maujood pointer, length, aur capacity ko copy karte hain. Hum heap par maujood us data ko copy _nahi_ karte jise pointer refer karta hai. Doosre shabdon mein, memory mein data representation Figure 4-2 jaisi dikhti hai.

Pehle, humne kaha tha ki jab ek variable scope se bahar jaata hai, toh Rust automatically `drop` function call karta hai aur us variable ke liye heap memory ko clean up karta hai. Lekin Figure 4-2 dikhata hai ki dono data pointers ek hi location par point kar rahe hain. Yeh ek problem hai: jab `s2` aur `s1` scope se bahar jayenge, toh woh dono ek hi memory ko free karne ki koshish karenge. Ise _double free_ error ke roop mein jaana jaata hai aur yeh un memory safety bugs mein se ek hai jinka humne pehle zikr kiya tha. Memory ko do baar free karne se memory corruption ho sakti hai, jo potentially security vulnerabilities ko janm de sakti hai.

Memory safety sunishchit karne ke liye, `let s2 = s1;` line ke baad, Rust `s1` ko ab valid nahi maanta. Isliye, jab `s1` scope se bahar jaata hai toh Rust ko kuch bhi free karne ki zaroorat nahi padti. Dekhein ki jab aap `s2` banane ke baad `s1` ko use karne ki koshish karte hain toh kya hota hai; yeh kaam nahi karega:

let s1 = String::from("hello");
let s2 = s1;

_Figure 4-4: `s1` ke invalidate hone ke baad memory mein representation_

Yeh hamari problem solve kar deta hai! Sirf `s2` ke valid hone ke saath, jab yeh scope se bahar jayega toh yeh akela hi memory ko free karega, aur kaam khatam.

Iske alawa, isse ek design choice implied hoti hai: Rust kabhi bhi automatically aapke data ki “deep” copies nahi banayega. Isliye, kisi bhi automatic copying ko runtime performance ke mamle mein sasta (inexpensive) maana ja sakta hai.

## 8. Scope and Assignment

Iske ulta bhi true hai scoping, ownership, aur `drop` function ke through memory free kiye jaane ke beech ke relationship ke liye. Jab aap kisi existing variable ko ek bilkul nayi value assign karte hain, toh Rust `drop` ko call karega aur original value ki memory ko turant free kar dega. Example ke liye, is code par vichar karein:

```rust
let mut s = String::from("hello");
s = String::from("ahoy");

println!("{s}, world!");
```

**Output:**

```shell
$ cargo run
ahoy, world!
```

Hum shuru mein ek variable `s` declare karte hain aur use `"hello"` value wale ek `String` se bind karte hain. Phir hum turant `"ahoy"` value ke saath ek naya `String` banate hain aur use `s` mein assign karte hain. Is point par, heap par original value ko ab kuch bhi refer nahi kar raha hai.

```text
s (stack)                     heap
┌──────────┬───────┐         ┌───────┬───────┐
│ name     │ value │         │ index │ value │
├──────────┼───────┤         ├───────┼───────┤
│ ptr      │  ─────┼──┐      │ 0     │ h     │  (dropped)
│ len      │ 4     │  │      │ 1     │ e     │
│ capacity │ 4     │  │      │ 2     │ l     │
└──────────┴───────┘  │      │ 3     │ l     │
                      │      │ 4     │ o     │
                      │      └───────┴───────┘
                      │
                      │      ┌───────┬───────┐
                      │      │ index │ value │
                      │      ├───────┼───────┤
                      └─────▶│ 0     │ a     │
                             │ 1     │ h     │
                             │ 2     │ o     │
                             │ 3     │ y     │
                             └───────┴───────┘
```

_Figure 4-5: Initial value ke replace hone ke baad memory mein representation_

Original string is tarah turant scope se bahar chali jaati hai. Rust is par `drop` function run karega aur iski memory turant free kar di jayegi. Jab hum aakhir mein value print karte hain, toh yeh `"ahoy, world!"` hogi.

## 9. Variables and Data Interacting with Clone

Agar hum waqai `String` ke heap data ko deeply copy karna chahte hain, na ki sirf stack data ko, toh hum `clone` naam ke ek common method ka use kar sakte hain. Hum Chapter 5 mein method syntax discuss karenge, lekin kyunki methods kai programming languages mein ek common feature hain, aapne unhe shayad pehle dekha hoga.

Yahan action mein `clone` method ka ek example diya gaya hai:

```rust
let s1 = String::from("hello");
let s2 = s1.clone();

println!("s1 = {s1}, s2 = {s2}");
```

**Output:**

```shell
$ cargo run
s1 = hello, s2 = hello
```

Yeh bilkul sahi kaam karta hai aur explicitly Figure 4-3 mein dikhaya gaya behavior produce karta hai, jahan heap data copy _hota_ hai.

Jab aap `clone` ko call dekhte hain, toh aapko pata hota hai ki koi arbitrary code execute ho raha hai aur woh code expensive ho sakta hai. Yeh ek visual indicator hai ki kuch alag ho raha hai.

## 10. Stack-Only Data: Copy

Ek aur wrinkle (pehlu) hai jiske baare mein humne abhi tak baat nahi ki hai. Yeh code integers ka use karta hai—jiska kuch hissa Listing 4-2 mein dikhaya gaya tha—jo kaam karta hai aur valid hai:

```rust
let x = 5;
let y = x;

println!("x = {x}, y = {y}");
```

**Output:**

```shell
$ cargo run
x = 5, y = 5
```

Lekin yeh code us cheez ke contradict lagta hai jo humne abhi seekhi hai: hamare paas `clone` ka call nahi hai, lekin `x` abhi bhi valid hai aur ise `y` mein move nahi kiya gaya tha.

Wajah yeh hai ki integers jaise types jinka compile time par ek known size hota hai, unhe poori tarah stack par store kiya jaata hai, isliye actual values ki copies banana jaldi hota hai. Iska matlab hai ki koi wajah nahi hai ki hum variable `y` banane ke baad `x` ko valid hone se rokna chahein. Doosre shabdon mein, yahan deep aur shallow copying ke beech koi difference nahi hai, isliye `clone` ko call karne se usual shallow copying se kuch alag nahi hoga, aur hum ise chhod sakte hain.

Rust mein ek special annotation hai jise `Copy` trait kaha jaata hai jise hum un types par rakh sakte hain jo stack par store hote hain, jaisa ki integers hain (hum traits ke baare mein Chapter 10 mein aur baat karenge). Agar koi type `Copy` trait ko implement karta hai, toh jo variables iska use karte hain woh move nahi hote, balki trivially copy ho jaate hain, jisse woh kisi doosre variable mein assignment ke baad bhi valid rehte hain.

Rust humein kisi type ko `Copy` ke saath annotate nahi karne dega agar us type, ya uske kisi bhi part ne, `Drop` trait ko implement kiya hai. Agar type ko tab kuch special hone ki zaroorat hai jab value scope se bahar jaati hai aur hum us type mein `Copy` annotation add karte hain, toh humein ek compile-time error milega. Yeh jaanne ke liye ki apne type mein `Copy` annotation kaise add karein taaki trait implement ho sake, Appendix C mein “Derivable Traits” dekhein.

Toh, kaunse types `Copy` trait ko implement karte hain? Aap sure hone ke liye diye gaye type ki documentation check kar sakte hain, lekin ek general rule ke roop mein, simple scalar values ka koi bhi group `Copy` implement kar sakta hai, aur kisi bhi aisi cheez ko jo allocation ki zaroorat rakhti hai ya kisi tarah ka resource hai, woh `Copy` implement nahi kar sakti. Yahan kuch aise types hain jo `Copy` implement karte hain:

- Saare integer types, jaise `u32`.
- Boolean type, `bool`, values `true` aur `false` ke saath.
- Saare floating-point types, jaise `f64`.
- Character type, `char`.
- Tuples, agar unmein sirf aise types hain jo khud bhi `Copy` implement karte hain. Example ke liye, `(i32, i32)` `Copy` implement karta hai, lekin `(i32, String)` nahi karta.

## 11. Ownership and Functions

Kisi function mein value pass karne ke mechanics kisi variable ko value assign karne ke similar hote hain. Kisi function mein variable pass karne se move ya copy hoga, bilkul waise hi jaise assignment karta hai. Listing 4-3 mein ek example hai jisme kuch annotations dikhate hain ki variables kahan scope mein aate hain aur kahan scope se bahar jaate hain.

**Filename: `src/main.rs`**

```rust
fn main() {
    let s = String::from("hello");  // s scope mein aata hai

    takes_ownership(s);             // s ki value function mein move ho jaati hai...
                                    // ... aur isliye ab yahan valid nahi hai

    let x = 5;                      // x scope mein aata hai

    makes_copy(x);                  // kyunki i32 Copy trait ko implement karta hai,
                                    // x function mein move nahi hota,
                                    // isliye iske baad bhi x ko use karna theek hai

} // Yahan, x scope se bahar jaata hai, phir s. Halanki, kyunki s ki value move ho gayi thi,
  // kuch special nahi hota.

fn takes_ownership(some_string: String) { // some_string scope mein aata hai
    println!("{some_string}");
} // Yahan, some_string scope se bahar jaata hai aur `drop` call hota hai. Backing
  // memory free kar di jaati hai.

fn makes_copy(some_integer: i32) { // some_integer scope mein aata hai
    println!("{some_integer}");
} // Yahan, some_integer scope se bahar jaata hai. Kuch special nahi hota.
```

_Listing 4-3: Annotated ownership aur scope ke saath functions_

**Output:**

```shell
$ cargo run
hello
5
```

Agar hum `takes_ownership` ke call ke baad `s` ko use karne ki koshish karein, toh Rust ek compile-time error throw karega. Yeh static checks humein galtiyon se bachate hain. `main` mein aisa code add karke dekhein jo `s` aur `x` ka use karta ho taaki aap dekh sakein ki aap unhe kahan use kar sakte hain aur kahan ownership rules aapko aisa karne se rokte hain.

## 12. Return Values and Scope

Values return karne se bhi ownership transfer ho sakti hai. Listing 4-4 ek aise function ka example dikhata hai jo kuch value return karta hai, jisme Listing 4-3 jaisi hi annotations hain.

**Filename: `src/main.rs`**

```rust
fn main() {
    let s1 = gives_ownership();        // gives_ownership apni return
                                       // value ko s1 mein move karta hai

    let s2 = String::from("hello");    // s2 scope mein aata hai

    let s3 = takes_and_gives_back(s2); // s2 ko takes_and_gives_back mein
                                       // move kiya jaata hai, jo apni
                                       // return value ko s3 mein bhi move karta hai

} // Yahan, s3 scope se bahar jaata hai aur drop ho jaata hai. s2 ko move kiya gaya tha, isliye kuch
  // nahi hota. s1 scope se bahar jaata hai aur drop ho jaata hai.

fn gives_ownership() -> String {       // gives_ownership apni
                                       // return value ko us function mein
                                       // move karega jo ise call karta hai

    let some_string = String::from("yours"); // some_string scope mein aata hai

    some_string                        // some_string return hota hai aur
                                       // calling function mein move ho jaata hai
}

// Yeh function ek String leta hai aur ek String return karta hai.
fn takes_and_gives_back(a_string: String) -> String {
    // a_string scope mein aata hai

    a_string  // a_string return hota hai aur calling function mein move ho jaata hai
}
```

_Listing 4-4: Return values ki ownership transfer karna_

Kisi variable ki ownership har baar ek hi pattern follow karti hai: kisi doosre variable ko ek value assign karne se woh move ho jaati hai. Jab koi variable jisme heap par data shaamil hai scope se bahar jaata hai, toh value ko `drop` dwara clean up kar diya jayega jab tak ki data ki ownership kisi doosre variable mein move na kar di gayi ho.

Jabki yeh kaam karta hai, har function ke saath ownership lena aur phir ownership wapas return karna thoda tedious (thakau) hota hai. Kya hoga agar hum chahte hain ki koi function kisi value ko use kare lekin uski ownership na le? Yeh kaafi annoying hai ki jo bhi cheez hum pass karein use wapas pass bhi karna pade agar hum use dobara use karna chahte hain, kisi bhi us data ke alawa jo function body se result ke roop mein aata hai jise hum shayad return bhi karna chahein.

Rust humein ek tuple ka use karke multiple values return karne deta hai, jaisa ki Listing 4-5 mein dikhaya gaya hai.

**Filename: `src/main.rs`**

```rust
fn main() {
    let s1 = String::from("hello");

    let (s2, len) = calculate_length(s1);

    println!("The length of '{s2}' is {len}.");
}

fn calculate_length(s: String) -> (String, usize) {
    let length = s.len(); // len() ek String ki length return karta hai

    (s, length)
}
```

_Listing 4-5: Parameters ki ownership return karna_

**Output:**

```shell
$ cargo run
The length of 'hello' is 5.
```

Lekin yeh ek aise concept ke liye bahut zyada ceremony aur bahut saara kaam hai jo common hona chahiye. Khushkismati se, Rust mein ownership transfer kiye bina kisi value ko use karne ke liye ek feature hai: _references_.
